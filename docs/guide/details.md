# Руководство Solo Repository

Solo Repository предоставляет типизированное чтение, явную запись, переводы с единым fallback и пакетную загрузку связей. [Быстрый старт](index.md) показывает подключение, [публичный API](api.md) описывает контракты. Для приложения на `solophp/base-repository` v3 есть [руководство по миграции](migration.md).

## Реализовано

Доступны `Mapping`, `Repository`, `ReadQuery`, `Filter::all/any/not/related`, `Visibility`, `Translations`, `TranslationStore`, четыре вида связей, `Load` и `LinkSet`. Реализованы чтение моделей и проекций, сортировка по полям целей `BelongsTo`, блокирующее чтение, count/exists, CRUD, атомарный insertMany, native upsert по уникальному ключу, soft delete, пакетный обход по ID, переводы с единым fallback и пакетная загрузка вложенных связей. Исполняемые примеры `examples/crud.php`, `examples/translations.php` и `examples/relations.php` используют SQLite в памяти:

```sh
composer install
php examples/crud.php
php examples/translations.php
php examples/relations.php
vendor/bin/phpunit --testsuite Core
composer test
```

`Mapping` принимает `translations` и `relations`. `withLocale()`, `with()` и `withVisibility()` возвращают независимые настройки чтения. `translations()` и `links()` дают отдельный API записи. Сценарии каталога и экспорта входят в интеграционные тесты.

Бюджет связанных параметров statement включает locale-параметры JOIN; keyset оставляет один из них для продолжения. По умолчанию это лимит платформы: 65 535 для PostgreSQL и MySQL/MariaDB, 32 766 для SQLite 3.32+, 900 для более старого SQLite и прочих платформ. Аргумент `parameterLimit` конструктора `Repository` задаёт другой положительный бюджет, например чтобы раньше отклонять большие IN-фильтры корня. Значение не должно превышать лимит сервера; повышать его стоит только на платформе, чей реальный лимит выше значения по умолчанию. Внутренние списки ключей (загрузка связей, `lockForUpdate()`, удаление в `LinkSet`) дополнительно ограничены 5 000 ключей на statement: более длинный IN-список может превысить память range optimizer MySQL и превратить поиск по индексу в полный скан. Создание репозиториев и запросов не открывает соединение: платформа определяется при построении первого statement. Имя таблицы пока простое, без schema-prefix. ID целочисленного PK принимается как int или каноническая десятичная строка: нечисловые значения и переполнение PHP integer для integer/smallint отклоняются. Это исключает превращение ошибочного ID в чужой числовой ключ. Значения критериев проверяются по типу поля по тому же принципу: integer-поле принимает int или каноническую десятичную строку; decimal — конечное число или десятичную строку без экспоненты; float — конечное число или числовую строку с конечным значением; boolean — `bool`, `0` или `1` (в том числе строкой); строковые поля — строку, целое или `Stringable`; enum — строку или `Stringable` (целое MySQL читает как номер элемента); `simple_array` — массив. Иначе драйвер молча превратил бы `'12x'` в 12, а MySQL — `'false'` в TRUE. Даты, интервалы и bcmath-числа проверяет сам DBAL; JSON, бинарные и пользовательские типы получают значение как есть. Проверяется форма значения, а не диапазон, точность или масштаб колонки: это остаётся ограничением базы. Например, SQLite хранит decimal как REAL, и слишком большое значение становится там бесконечностью.

Основной набор тестов использует SQLite. Отдельный набор `Database` выполняется на реальных MySQL 8.4, MariaDB 12.3 и PostgreSQL 17 с native PDO prepares. Он запускается отдельно от `composer test`: отсутствие URL, недоступная БД и пропущенные тесты считаются ошибками.

Solo Repository превращает строки БД в обычные PHP-объекты, разрешает переводы с fallback и загружает связи пакетами. Doctrine DBAL остаётся SQL API. Пакет не отслеживает изменения объектов и не сохраняет граф автоматически.

## Проверка на MySQL, MariaDB и PostgreSQL

Общий набор из 37 тестов проверяет generated ID и CRUD, преобразование decimal/bool/date/JSON, soft delete и keyset, native upsert строк и PATCH upsert переводов, единый fallback, четыре типа связей, вложенные EXISTS и сортировку по путям `BelongsTo`. Блокирующее чтение проверяется второй сессией: какие строки держит блокировка и чем такое чтение отличается от снимка транзакции REPEATABLE READ на каждой СУБД. Отдельные сценарии проверяют пакетные границы, запрос с максимальным для сервера числом параметров (65 535), сортировку коллекции из 905 элементов, освобождение предыдущей страницы, строковые ключи и native PostgreSQL UUID, rollback позднего пакета и продолжение внешней транзакции после savepoint. Схемы содержат настоящие FK и UNIQUE; тесты выполняют SQL на серверах без моков платформ.

`.github/workflows/tests.yml` сохраняет три задания основного SQLite-набора и запускает `Database` на каждой из трёх СУБД для тех же комбинаций:

| PHP | Ограничение DBAL при установке |
|---|---|
| 8.3 | `4.3.*` — минимальная поддерживаемая ветка |
| 8.3 | `^4.3` — актуальная совместимая версия |
| 8.5 | `^4.3` — актуальная совместимая версия |

Для своей тестовой БД нужен `REPOSITORY_DATABASE_URL` и соответствующее расширение `pdo_mysql` или `pdo_pgsql`. Поддерживаются URL `mysql://` (MySQL и MariaDB) и `postgresql://`; имя БД должно заканчиваться на `_test`. Набор создаёт и удаляет свои fixture-таблицы с префиксом `repo_`, поэтому ему нужна отдельная тестовая БД:

```sh
REPOSITORY_DATABASE_URL='mysql://repository:repository@127.0.0.1:3306/repository_test' composer test:database
REPOSITORY_DATABASE_URL='postgresql://repository:repository@127.0.0.1:5432/repository_test' composer test:database
```

Локально достаточно Docker с Compose v2. `compose.database.yml` создаёт проект `solo-repository-database`, MySQL 8.4, MariaDB 12.3, PostgreSQL 17 и PHP runner. Порты на хост не публикуются, данные всех БД находятся в tmpfs. Runner монтирует репозиторий только для чтения; зависимости устанавливаются отдельной командой до запуска тестов:

```sh
docker compose -f compose.database.yml build tests
docker run --rm -v "$PWD":/workspace -w /workspace \
  solo-repository-database-tests:local composer install --no-interaction --prefer-dist

# MySQL — URL по умолчанию.
docker compose -f compose.database.yml run --rm tests

# MariaDB и PostgreSQL — тот же набор, другой URL.
REPOSITORY_DATABASE_URL='mysql://repository:repository@mariadb:3306/repository_test' \
  docker compose -f compose.database.yml run --rm tests
REPOSITORY_DATABASE_URL='postgresql://repository:repository@postgres:5432/repository_test' \
  docker compose -f compose.database.yml run --rm tests

# Удалить контейнеры, сеть и временные данные.
docker compose -f compose.database.yml down --volumes --remove-orphans
```

Compose дожидается healthcheck всех трёх БД. Команда runner — `php vendor/bin/phpunit -c phpunit.database.xml --do-not-cache-result`; ошибки соединения не превращаются в skip. Для выбора PHP передайте `PHP_VERSION=8.5` при сборке. Для локальной проверки минимальной ветки DBAL можно вместо `composer install` выполнить в том же runner `composer update --with='doctrine/dbal:4.3.*'`; это изменит локальные `composer.lock` и `vendor`. После такой проверки верните нужную версию зависимостей.

MySQL 8.4, MariaDB 12.3 и PostgreSQL 17 — проверяемые серверные платформы Solo Repository. MariaDB использует те же ветки кода, что и MySQL (generated ID, upsert строк и переводов); в блокирующем чтении у неё нет `FOR UPDATE OF`. Другие платформы не поддерживаются.

## Основные решения

| Область | Решение |
|---|---|
| Основа | PHP ≥ 8.3, Doctrine DBAL 4.x с исходным минимумом 4.3. Без новых runtime-зависимостей |
| Модель | Любой объект; явная функция `hydrate(array): object`. Базовый `Entity` и reflection не нужны |
| Конфигурация | Один неизменяемый `Mapping`: таблица, типы колонок, ключ, mapper и необязательные возможности |
| Чтение | `Repository` создаёт независимый `ReadQuery`; `withLocale()` и `with()` сохраняются |
| Запись | Явные операции над данными; результат — affected rows либо явно запрошенный ID. Автоматического перечитывания модели нет |
| Переводы | Один resolver для значения в SELECT, фильтре и сортировке; fallback по каждому полю |
| Связи | Явные определения и функции присвоения; пакетная загрузка вместо запросов из объектов |
| Сложный SQL | Настоящий DBAL `QueryBuilder`: `ReadQuery::queryBuilder()` с критериями Mapping либо через уже имеющийся `Connection` |

Не входят в 1.0: Unit of Work, identity map, lazy proxies, dirty tracking, каскадное сохранение графа, генерация схемы, query cache, event bus, advisory locks, собственный контейнер и отдельные Composer-пакеты. Приложение определяет бизнес-операции, транзакции между несколькими репозиториями и правила повторных попыток.

## Устройство

```text
Repository<T> ── Mapping<T> + Connection
   │
   ├── read() / withLocale() / with() → ReadQuery<T>
   │      └── terminal → DBAL QueryBuilder → typed rows → hydrate
   │                                              └── batch relations → assign
   │
   ├── insert / update / delete → DBAL
   ├── translations() → TranslationStore
   └── links(name) → LinkSet
```

Публичные типы: `Repository<T>`, `Mapping<T>`, `ReadQuery<T>`, `Filter`, `Visibility`, `Load`, `Translations`, четыре определения связей, `TranslationStore` и `LinkSet`. Тип `T` задаётся PHPDoc generics для статического анализа и ковариантен; определения связей параметризованы владельцем и целью, поэтому анализатор проверяет `assign` по Mapping цели. Runtime проверяет, что mapper и assign возвращают объект. Namespace `Internal` и элементы с `@internal` не являются поддерживаемым API приложения: конструкторы `ReadQuery`, `LinkSet` и `TranslationStore` (их получают из `Repository`), свойства `Filter` и `Relation::resolve()`.

Внутри достаточно небольших компонентов по ответственности:

- `Database`: соединение плюс сведения о платформе (диалект, лимит параметров, экранирование), получаемые лениво.
- `ReadExecutor`: создаёт новый DBAL builder для каждого выполнения.
- `PredicateCompiler`: проверяет фильтры целиком, сворачивает константы в типизированное дерево условий и переводит его в выражения и параметры DBAL.
- `FieldResolver`: проверяет колонку и возвращает обычное либо локализованное SQL-выражение.
- `RowMapper`: применяет типы DBAL и вызывает пользовательский mapper.
- `RelationLoader`: группирует строки, пакетно получает связи и вызывает `assign`.
- `Repository`, `TranslationStore` и `LinkSet`: явные операции записи, включая узкие платформенные варианты upsert и получения generated ID.

У пакета нет собственного общего SQL AST, диалектного движка и публичных методов `select/from/join/groupBy/having`. Для таких запросов приложение использует DBAL напрямую. Чтобы сохранить в таком SQL критерии Mapping, `ReadQuery::queryBuilder($alias, $criteria)` отдаёт DBAL `QueryBuilder` с таблицей под псевдонимом во FROM, критериями и видимостью в WHERE и JOIN переводов, которые нужны критериям при locale запроса. SELECT в нём нет: его, как и JOIN, группировку и сортировку, добавляет приложение. Свои условия добавляются через `andWhere()`, а не `where()`: `where()` в DBAL заменяет всё условие WHERE, и критерии вместе с мягким удалением молча пропадут. Псевдоним — SQL-идентификатор в нижнем регистре, чтобы ссылки без кавычек вроде `s.product_id` совпадали с ним на всех платформах; JOIN переводов называются `<alias>_translation` и `<alias>_fallback`. Значения критериев привязаны именованными параметрами, поэтому свои значения тоже привязываются через `createNamedParameter()`. Список `IN` — один параметр типа `ArrayParameterType`, который DBAL разворачивает при выполнении, поэтому SQL построителя выполняется самим построителем или вместе с `getParameterTypes()`. Всё добавленное приложением — обычный DBAL: присоединённые таблицы не получают видимости и locale, а строки результата не преобразуются типами Mapping. Непустой `with()` вызывает ошибку.

## Mapping и модели

`Mapping` содержит `table`, `columns`, `hydrate`, `primaryKey = 'id'` (NULL для таблицы без одноколоночного ключа), `generatedId = true`, а также необязательные `translations`, `relations` и `softDeleteColumn`.

`hydrate` может быть NULL у таблицы, которую читают только строками, например у таблицы связей без своей модели. Для неё работают `rows()`, агрегаты, `queryBuilder()`, связанные фильтры и запись, а `find()`, `findOneBy()`, `findBy()`, `iterateById()` и загрузка её как цели связи бросают `LogicException` до SQL.

`columns` — ассоциативный массив `имя_колонки => DBAL type name`. Эти имена используются в фильтрах, сортировке, записи и строковых результатах. Это одновременно allowlist: неизвестное поле вызывает ошибку до SQL. CamelCase, приватные свойства и конструкторы остаются задачей mapper. SQL-идентификаторы проверяются и экранируются средствами DBAL; значения всегда передаются параметрами.

Поддерживается один первичный ключ `int|string` либо его отсутствие. `primaryKey: null` описывает таблицу без одноколоночного ключа, например с составным ключом: её строки читаются, вставляются и меняются по критериям (`findBy`, `rows`, `count`, агрегаты, `queryBuilder`, `insert`, `insertMany`, `updateBy`, `deleteBy`, `purgeBy`). Операции по ID (`find`, `insertGetId`, `update`, `delete`, `restore`, `purge`, `lockForUpdate`) бросают `LogicException`, а `iterateById` — `InvalidArgumentException`, всё до SQL. Сгенерированного ID у такой таблицы нет, а вставляемая строка содержит хотя бы одну колонку.

Без первичного ключа нет переводов, а из связей возможен только `BelongsTo`: `HasOne`, `HasMany` и `BelongsToMany` находят владельца по его ключу. Такую таблицу могут загружать `HasOne` и `HasMany`, но не `BelongsTo` и `BelongsToMany`, которые ссылаются на ключ цели. `Filter::related` по её `BelongsTo` работает с любым типом ключа, а загрузка требует целочисленного ключа цели: строковые ключи сравниваются по collation базы в SQL через первичный ключ владельца. Адресация строки по составному ключу и связи по альтернативным уникальным ключам остаются за границами 1.0. Mapper получает все объявленные основные и переведённые колонки, а не `SELECT *`.

Заданный PK обязательно входит в `columns`; FK связи входит в `columns` соответствующей стороны. `generatedId: true` допустим только для совместимого целочисленного PK. Собственный Mapping проверяется сразу, требования к ленивой целевой стороне — при первом разрешении связи.

После чтения типы преобразуются через DBAL перед вызовом `hydrate`. Например, `decimal` остаётся строкой, а `datetime_immutable` становится `DateTimeImmutable`. На запись и в сравнения DBAL получает имя типа и выполняет преобразование один раз. Список `IN` после проверки каждого элемента преобразуется типом поля в значения БД и связывается одним параметром-списком DBAL, который DBAL разворачивает при выполнении; тип без списочного связывания, например boolean, связывает каждый элемент отдельно. В бюджет параметров список входит каждым значением. Пользовательские типы регистрируются в DBAL; второй реестр codecs не создаётся. Типы, требующие специальных SQL-обёрток, в первый контракт не входят.

Для загрузки связей ключи сохраняются из **преобразованных строк**, до `hydrate`. Loader не читает `$model->id` или `$model->category_id`. Типы связанных ключей должны быть совместимы. Для строковых ключей FK и соответствующий PK должны использовать одинаковые правила сравнения (collation). Фабрика `target` возвращает Mapping цели и вызывается отложенно, что допускает циклическую конфигурацию; отдельный registry не нужен. Связанные строки читаются через соединение репозитория владельца.

## Публичное чтение

У `Repository<T>` три точки входа в чтение:

```php
read(): ReadQuery;                         // настройки по умолчанию
withLocale(string $locale, ?string $fallback = null): ReadQuery;
with(array $relations): ReadQuery;         // list<string|Load>
```

Последние две — короткие формы `read()->withLocale(...)` и `read()->with(...)`. Обычное чтение выглядит как `$products->read()->find($id)`. Бизнес-методы приложения живут в сервисе, который владеет репозиторием, или в типизированном наследнике `Repository`: `readonly`-класс задаёт маппинг в своём конструкторе, контейнер внедряет его по типу, а статический анализ берёт модель из `@extends Repository<Model>`. Публичные методы `Repository` final — наследник добавляет свои методы, но не меняет унаследованные чтения и записи.

Контракт `ReadQuery<T>`:

```php
withLocale(string $locale, ?string $fallback = null): self;
with(array $relations): self;              // list<string|Load>
withVisibility(Visibility $visibility): self;
forUpdate(): self;                         // блокирующее чтение

find(int|string $id): ?object;             // T|null
findOneBy(array|Filter $criteria, array $orderBy = []): ?object;
findBy(
    array|Filter $criteria = [],
    array $orderBy = [],
    ?int $limit = null,
    int $offset = 0,
): array;                                 // list<T>
exists(array|Filter $criteria = []): bool;
count(array|Filter $criteria = []): int;
sum(string $field, array|Filter $criteria = []): mixed;   // 0 своего типа, если строк нет
min(string $field, array|Filter $criteria = []): mixed;   // NULL, если строк нет
max(string $field, array|Filter $criteria = []): mixed;
avg(string $field, array|Filter $criteria = []): ?float;
rows(
    array $columns,
    array|Filter $criteria = [],
    array $orderBy = [],
    ?int $limit = null,
    int $offset = 0,
): array;                                 // list<array<string, mixed>>
iterateById(array|Filter $criteria = [], int $batchSize = 500): iterable;
queryBuilder(string $alias, array|Filter $criteria = []): QueryBuilder;
```

Каждый `with*` возвращает новый объект. Terminal-методы не сбрасывают настройки: запрос можно повторять и независимо разветвлять. `with()` заменяет весь список загрузок, `with([])` очищает его. DBAL builder никогда не хранится как разделяемое изменяемое состояние.

`find` и `findOneBy` ограничивают SQL одной строкой. `exists` запрашивает константу с LIMIT 1. `count` считает корневые записи; загрузки `with()` на эти две операции не влияют. Ни один из этих методов не делает дополнительный COUNT для пагинации.

`sum`, `min`, `max` и `avg` агрегируют одно читаемое поле (в том числе переводимое — с locale запроса) по тем же строкам, что считает `count`: те же критерии, relation predicates и видимость. Итог для отфильтрованного списка совпадает с его фильтром. `sum`, `min` и `max` преобразуют результат DBAL-типом поля: сумма decimal — точная строка, `max('created_at')` — `DateTimeImmutable`. Без подходящих строк `sum` возвращает ноль типа поля, остальные — NULL. `sum` и `avg` принимают только поля smallint, integer, bigint, decimal, float и smallfloat; другие поля отклоняются до SQL. Агрегаты по нескольким таблицам строятся через DBAL.

`rows` возвращает только запрошенные, преобразованные по DBAL типам колонки. Он не создаёт частично заполненные модели. Непустой `with()` для `rows` вызывает ошибку, а не молча игнорируется; можно использовать отдельную ветку запроса с `with([])`.

Без `orderBy` порядок не определён. Для стабильной страницы приложение добавляет уникальный ключ в конец сортировки. Отрицательные limit/offset и неизвестные направления сортировки отклоняются; `limit: 0` возвращает пустой список. Коллекции `findBy()` материализуются полностью в пределах указанного limit.

Ключ `orderBy` в `findBy`, `findOneBy` и `rows` может быть путём через связи `BelongsTo` к полю цели: `['category.name' => 'ASC']`, `['category.parent.name' => 'DESC']`. Каждая цель пути присоединяется LEFT JOIN по первичному ключу один раз на statement — по тем строкам, которые видит загрузка той же связи в этом чтении: по активным, если чтение не загружает связь с другой видимостью. Поэтому список, который показывает мягко удалённые категории через `with([new Load('category', visibility: Visibility::All)])`, сортируется и по их именам; от загрузки берётся только видимость, не её критерии. Строка с пустой, висячей или невидимой ссылкой сортируется как строка с NULL в этом поле, а место NULL задаёт БД (в начале по возрастанию на MySQL, MariaDB и SQLite, в конце на PostgreSQL). Переводимое поле цели читается в locale и fallback запроса — цель наследует их так же, как загрузка связей. Пути через `HasOne`, `HasMany` и `BelongsToMany` могли бы дать несколько строк и отклоняются до SQL. Порядок to-many связи по умолчанию и порядок `Load` принимают те же пути, от маппинга цели.

`forUpdate()` даёт то же чтение блокирующим: `find`, `findOneBy`, `findBy`, `rows`, `exists` и каждый пакет `iterateById` выполняют `SELECT ... FOR UPDATE` и держат прочитанные строки до конца транзакции; вне транзакции они бросают `LogicException`. Обычное чтение в транзакции REPEATABLE READ отвечает из её снимка, а блокирующее никогда не возвращает устаревшую версию строки: MySQL читает последнюю зафиксированную, PostgreSQL и MariaDB (с `innodb_snapshot_isolation`, по умолчанию начиная с 11.6) отклоняют строку, изменённую после снимка, ошибкой сериализации — транзакцию нужно начать заново. Блокируются строки таблицы самого чтения: PostgreSQL и MySQL 8 получают `FOR UPDATE OF`, а MariaDB, где его нет, блокирует и присоединённые строки переводов и сортировки. Загрузки связей читаются без блокировок. Агрегаты и `queryBuilder()` блокирующего чтения бросают `LogicException`. В SQLite строковых блокировок нет, выполняется обычный SELECT. Строки блокируются в том порядке, в каком их читает БД; транзакции, которые блокируют пересекающиеся наборы строк, читают их в порядке ключа или сначала берут `lockForUpdate()`. MySQL и MariaDB блокируют каждую строку, прочитанную ради ответа, поэтому при сортировке, которую не обслуживает индекс (например, по пути связи), чтение с limit блокирует все подходящие строки, а не только страницу.

## Фильтры без второго QueryBuilder

Обычный массив — AND по полям:

```php
['status' => 'active', 'price >=' => '50.00', 'id IN' => [1, 2, 3]]
```

Поддерживаются операторы `=`, `!=`, `>`, `>=`, `<`, `<=`, `IN`, `NOT IN`, `LIKE`, `NOT LIKE`; отсутствие суффикса означает `=`. `= null` и `!= null` превращаются в IS NULL и IS NOT NULL. NULL с прочими операторами, NULL внутри IN и массив без явного IN отклоняются. `IN []` означает false, `NOT IN []` — true. LIKE использует SQL wildcard-семантику; регистр, collation и порядок NULL зависят от БД.

Ключ задаёт и поле, и оператор, поэтому ключи критериев строятся только из фиксированных строк в коде, а не из параметров запроса и других входных данных. Кто управляет ключом, тот выбирает оператор: `filter[price >=]=0` превратит равенство в сравнение. Если пользователь выбирает поля фильтра, сопоставьте каждое разрешённое имя с фиксированным ключом.

Четыре конструктора `Filter` нужны для группировки и отношений:

```php
Filter::all(array|Filter ...$parts): Filter;
Filter::any(array|Filter ...$parts): Filter;
Filter::not(array|Filter $part): Filter;
Filter::related(
    string $relation,
    array|Filter $criteria = [],
    Visibility $visibility = Visibility::Active,
): Filter;
```

`all` и `any` требуют хотя бы один аргумент. Пустой массив означает true. Логические группы сохраняются буквально; простые константы нормализуются. NOT следует SQL three-valued logic: например, `NOT(price > 10)` не включает NULL-цены автоматически.

`related('tags', ['color' => 'red', 'size' => 'large'])` означает **одну** связанную строку с обоими признаками и компилируется в EXISTS. Два отдельных `related('tags', ...)` в `all` допускают две разные строки. `not(related(...))` — NOT EXISTS. OR внутри related остаётся OR. Корневые записи не размножаются от совпавших связей.

Имена `tags.slug`, SQL-фрагменты, скрытые scope-ключи и неизвестные поля не принимаются. Вложенные связи выражаются вложенными `related`, а не неоднозначным разбором точки. У каждого EXISTS собственные alias и параметры. Сортировка по коллекции не поддерживается: её агрегат и JOIN задаются через DBAL.

Произвольный корневой фильтр с большим IN не разбивается на несколько запросов: это изменило бы семантику OR, сортировки и limit. Превышение бюджета параметров даёт явную ошибку; иной способ передать большой набор задаётся через DBAL. Автоматическое разбиение относится только к внутренним пакетам loader и bulk insert.

## Переводы

`Translations` задаёт `table`, `foreignKey`, `columns`, необязательный `defaultLocale` и `localeColumn = 'locale'`. В первом релизе переводимые поля — nullable string/text; их имена не пересекаются с основными колонками. Нужен UNIQUE `(foreignKey, localeColumn)` и внешний ключ на основную таблицу. Для переносимого PATCH upsert эта пара должна быть единственным возможным конфликтом уникальности при вставке переводимых данных; дополнительные UNIQUE по переводимым полям требуют отдельной операции приложения. Это ограничение учитывает поведение [MySQL ON DUPLICATE KEY](https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html).

UNIQUE должен обеспечивать одну строку на владельца и locale с теми же правилами сравнения ID, что и PK владельца. Например, для строкового PK с `COLLATE NOCASE` в SQLite колонка translation FK тоже требует `COLLATE NOCASE`: бинарный UNIQUE позволил бы два перевода для `Owner` и `owner`, хотя это один владелец. Согласованные типы, collation и ограничения задаются миграциями приложения, без автоматической интроспекции схемы в репозитории.

Служебные `foreignKey` и `localeColumn` не входят в переводимые `columns` и недоступны в patch.

Обычное чтение использует `defaultLocale` без fallback. Без `defaultLocale` чтение, которое не называет locale, не делает translation JOIN: переводимые поля приходят NULL, а условия, сортировки и агрегаты по ним бросают `LogicException`, пока чтение не вызовет `withLocale()`. `withLocale('uk', fallback: 'en')` явно выбирает пару. Неявного глобального языка, цепочки fallback и fallback к колонке основной таблицы нет. Пустая locale отклоняется; совпадающие primary/fallback сворачиваются в один язык.

| Значение для `uk` | Значение для `en` | Результат с fallback `en` |
|---|---|---|
| Нет строки | `"Chair"` | `"Chair"` |
| NULL | `"Chair"` | `"Chair"` |
| `""` | `"Chair"` | `""` |
| `"0"` | `"Chair"` | `"0"` |
| `"Стілець"` | `"Chair"` | `"Стілець"` |
| NULL | Нет строки | NULL |

Таким образом, fallback выражается `COALESCE(primary.field, fallback.field)`. Для каждого поля выбор независим. Без fallback отсутствующая строка/NULL дают NULL. Mapper должен допускать это значение либо применять явно выбранное приложением правило.

Один `FieldResolver` применяется к проекции, WHERE, ORDER BY и условиям внутри связей. Фильтр по `name` проверяет именно то значение с fallback, которое будет показано. Это намеренное отличие от v3, где fallback выборки и условия могли расходиться.

Эффективная пара языков корневого чтения наследуется связями и relation predicates. Если у корня нет ни `withLocale()`, ни `defaultLocale`, в каждой ветви первая переводимая сущность с `defaultLocale` применяет его, далее он наследуется; переводимые сущности выше неё читают NULL в переводимых полях. Для одного языка всего графа достаточно задать `withLocale()` у корня, даже если он сам не переводится. Переопределения языка отдельной загрузки в 1.0 нет.

При чтении модели из переводимого репозитория с `defaultLocale` этот язык означает JOIN по умолчанию. `rows`, `count` и `exists` добавляют translation JOIN только когда их поля/фильтры этого требуют. Нелокализованные физические строки можно читать напрямую через DBAL; отдельный `withoutLocale()` не нужен.

`TranslationStore` отделяет редактирование от отображения:

```php
get(int|string $id, string $locale): ?array;           // собственные поля, без fallback
all(int|string $id): array;                            // все локали владельца, по возрастанию
save(int|string $id, string $locale, array $patch): void;
seed(int|string $id, array $locales, array $values): int;   // вставленные строки
delete(int|string $id, string $locale): int;
```

`save` — атомарный upsert **только переданных полей**. Значения patch принимаются как string или NULL. Пропущенное поле не изменяется, NULL включает fallback при чтении, `""` сохраняет пустой перевод. При создании строки неприсланные переводимые поля получают значение по умолчанию колонки; у колонки без DEFAULT это NULL, и при чтении сработает fallback. Пустой patch — no-op после проверки ID и locale. Переведённые поля в обычном `insert/update` и критериях записи отклоняются. Операции store используют физический ID, включая soft-deleted владельца; правила админского редактирования задаёт приложение.

Сохранение выполняет один native upsert: `ON CONFLICT` на SQLite/PostgreSQL или `ON DUPLICATE KEY UPDATE` на MySQL/MariaDB. Оно участвует в транзакции переданного DBAL connection; ошибки FK и ограничений не подавляются. Для других платформ непустой `save` вызывает ошибку до выполнения SQL. При отсутствии `Mapping.translations` вызов `Repository::translations()` тоже даёт явную ошибку.

`seed` создаёт перевод для каждой locale, у которой его ещё нет, — например, для всех активных языков новой сущности — и возвращает число вставленных строк. Существующие строки не меняются, поэтому повторный seed безопасен. Значения подчиняются правилам `save`, неприсланные поля новой строки получают значение по умолчанию колонки. Пропускается только конфликт по паре `(foreignKey, localeColumn)`: `ON CONFLICT ... DO NOTHING` на PostgreSQL/SQLite и no-op `ON DUPLICATE KEY UPDATE` на MySQL/MariaDB, без `INSERT IGNORE`. Ошибки FK и прочих ограничений по-прежнему пробрасываются.

`get` возвращает все объявленные переводимые поля с DBAL conversion. NULL вместо массива означает отсутствие строки; существующая строка со всеми NULL возвращает массив. `all` возвращает те же поля для каждой сохранённой локали владельца, ключи — локали по возрастанию; без переводов — пустой массив.

## Связи

Определения `BelongsTo`, `HasOne`, `HasMany`, `BelongsToMany` содержат отложенный `target: Closure(): Mapping` и `assign: Closure(entity, related): entity`. Фабрика `target` вызывается один раз, при первом использовании, и её Mapping запоминается для маппинга-владельца. `assign` можно не указывать у связи, по которой только фильтруют или которой пользуются через `links()`; загрузка такой связи бросает `LogicException` до SQL. В PHPDoc это `callable(TOwner, ?TTarget): TOwner` для to-one и `callable(TOwner, list<TTarget>): TOwner` для to-many. `assign` возвращает исходный объект после setter либо новую immutable-модель. Для to-one аргумент — объект или NULL, для to-many — список, включая пустой.

Описания связей Solo Repository находятся в namespace `Solo\Repository\Relations` (во множественном числе). Namespace `Solo\BaseRepository\Relation` относится к прежнему пакету `solophp/base-repository`.

У `BelongsTo` `foreignKey` находится у владельца; у `HasOne/HasMany` — у целевой таблицы. В обоих случаях ссылка ведёт на primary key. У `BelongsToMany` задаются `pivotTable`, `foreignPivotKey`, `relatedPivotKey`; UNIQUE по паре ключей и оба FK обязательны. Pivot с дополнительными атрибутами моделируется отдельным репозиторием.

`HasMany` и `BelongsToMany` принимают необязательный `orderBy` — порядок коллекции по умолчанию для каждой загрузки (например, изображения по `position`). `Load` с собственным непустым `orderBy` его заменяет.

```php
$query = $query->with([
    'category',
    new Load('tags', criteria: ['enabled' => true], orderBy: ['name' => 'ASC']),
]);
```

`Load(name, criteria = [], orderBy = [], visibility = Visibility::Active)` — настройки конкретной связи. `with(['category.parent'])` означает конечный путь загрузки, а не рекурсивный обход графа. Конфликтующие описания одного пути и неизвестные связи вызывают ошибку. Условие Load ограничивает загружаемую коллекцию; оно **не фильтрует владельцев**. Для отбора владельцев используется `Filter::related`, и его условия не меняют содержимое `with()` автоматически.

`Load` также принимает полный путь, например `Load('category.parent', ...)`. Строки создают структуру пути; явный Load задаёт настройки конкретного ребра. Поэтому `with([new Load('category', visibility: Visibility::All), 'category.parent'])` включает удалённую category, но её parent остаётся Active. Различающиеся явные настройки одного точного пути считаются конфликтом.

Loader выполняет один запрос для to-one/has-many и два для many-to-many: pivot, затем связанные модели. Это бюджет на путь и пакет ключей, а не обещание двух запросов при любом объёме. Большие IN разбиваются с учётом бюджета параметров и уже связанных параметров. Translation JOIN не добавляет отдельного round-trip.

Целочисленные ключи сравниваются по значению: цель `BelongsTo` выбирается по уникальным FK, гидрируется один раз и передаётся всем владельцам одним объектом; `HasOne/HasMany` выбираются по `fk IN (...)` без JOIN владельцев. Строковые ключи сопоставляются в SQL через JOIN с таблицей владельца, чтобы равенство следовало collation БД; каждая отличающаяся цель всё равно гидрируется один раз.

Единица пакета many-to-many — владельцы. Target SELECT ограничивается EXISTS по pivot и пакету owner IDs, а не списком всех target IDs. Все targets одного владельца сортируются в одном SQL-запросе; loader обходит этот результат в порядке БД и распределяет по pivot. Конкатенация независимо отсортированных target-чанков или PHP-сортировка вместо collation БД не используются.

Отбор/limit владельцев выполняется до загрузки коллекций. Результаты связываются по typed row keys. Непустой `Load.orderBy` задаёт порядок элементов каждой коллекции; без него порядок не гарантируется. `HasOne` требует уникальности внешнего ключа в целевой таблице; несколько совпадений — ошибка данных. `limit per parent`, lazy loading, cross-connection связи и автоматические каскады исключены из 1.0.

Незагруженные связи остаются в состоянии, заданном mapper. Загруженная to-one без видимой цели присваивается как NULL. Наличие одной PHP-инстанции для одной строки между запросами не гарантируется.

## Soft delete

`softDeleteColumn` должна присутствовать в `Mapping.columns` с nullable datetime-типом. Чтение по умолчанию добавляет IS NULL. `Visibility::All` снимает ограничение, `Visibility::Deleted` добавляет IS NOT NULL; при отсутствии soft delete `Active/All` эквивалентны, а `Deleted` — ошибка конфигурации запроса.

`withVisibility()` меняет только корень. Связи и relation predicates по умолчанию используют `Active`; `Load.visibility` и `Filter::related(..., visibility: ...)` переопределяют это явно. Translation JOIN не имеет собственного soft delete.

Условие видимости добавляется снаружи пользовательской группы: `visible AND (criteria)`. Указание `deleted_at` в критериях не отключает его. Поэтому `not(related('tags', []))` означает отсутствие **видимых** тегов.

`update/updateBy` изменяют только активные строки; изменение колонки soft delete через patch запрещено. `delete/deleteBy` ставят UTC timestamp только активным строкам; повторное удаление возвращает 0 и сохраняет прежний timestamp. Без soft delete эти методы удаляют физически. `restore(id)` очищает timestamp только у удалённой строки и требует настройки soft delete. `purge(id)` и `purgeBy(criteria)` физически удаляют строки независимо от видимости; пустой критерий `purgeBy` отклоняется, как у `deleteBy`. Очистка переводов/pivot при физическом удалении определяется FK и миграциями приложения.

## Запись и транзакции

Контракт записи `Repository<T>`:

```php
insert(array $data): int;                              // affected rows
insertGetId(array $data): int|string;                  // ID, не affected rows
insertMany(array $rows, int $batchSize = 500): int;     // affected rows
upsert(array $key, array $data, array $onInsert = []): void;
update(int|string $id, array $patch): int;
updateBy(array|Filter $criteria, array $patch): int;
delete(int|string $id): int;
deleteBy(array|Filter $criteria): int;
restore(int|string $id): int;
purge(int|string $id): int;
purgeBy(array|Filter $criteria): int;
lockForUpdate(int|string|array $ids): void;            // только внутри транзакции
translations(): TranslationStore;
links(string $relation): LinkSet;                      // только BelongsToMany
```

`insert` и `insertGetId` каждый выполняют вставку: вызывать их последовательно для одной записи нельзя. При `generatedId: false` ID обязателен. При `generatedId: true` разрешён переданный ID либо генерация integer identity/sequence. UUID, генерируемые на стороне БД, не входят в этот контракт; UUID приложения передаётся явно.

Явный ID допустим, только если его разрешает схема БД. Пакет не добавляет override для GENERATED ALWAYS и не синхронизирует sequence после ручной вставки.

Для MySQL при `generatedId: true` явный нулевой ID отклоняется: без NO_AUTO_VALUE_ON_ZERO сервер может заменить его новым ключом. Для генерации ключа ID нужно опустить.

`insertGetId` использует переданный ID либо проверенную стратегию платформы и возвращает ключ после преобразования по его типу Mapping. PostgreSQL получает ключ через INSERT RETURNING, MySQL/SQLite — через предусмотренное драйвером получение ID. Возможный служебный обмен с БД для ID не считается перечитыванием модели; обещания «всегда один SQL» здесь нет.

Patch не меняет пропущенные поля; NULL записывает SQL NULL. Записываемые значения до SQL проверяются по типу колонки по тем же правилам, что и значения критериев: `update($id, ['quantity' => 'abc'])` выбрасывает исключение, а не записывает 0. Primary key изменять нельзя. Пустой patch возвращает 0 без SQL. Для `updateBy/deleteBy` разрешены только основные колонки и логические группы; relation/translation predicates отклоняются, чтобы не обещать переносимый UPDATE/DELETE с JOIN.

Пустой критерий или критерий, свёрнутый простыми правилами к true, для массовой записи отклоняется до применения soft-delete условия. Это защита от пустого фильтра, а не доказательство безопасности любого логического выражения. Намеренное изменение всей таблицы выражается прямо через DBAL.

`insertMany` принимает строки с одним набором полей; порядок ключей неважен. Различающиеся наборы отклоняются до первой записи. Пустой список возвращает 0. Чанки учитывают лимит параметров; вся операция атомарна: пакет, который помещается в один statement, выполняется этим statement без транзакции, а разбитый — в одной транзакции/savepoint. Как и неудачный `insert`, такой пакет, упавший внутри транзакции вызывающего на PostgreSQL, обрывает эту транзакцию; к своему savepoint откатывается только разбитый пакет. Возвращаемый affected count зависит от драйвера: 0 от UPDATE не доказывает отсутствие записи.

`upsert(key, data, onInsert)` записывает строку уникального ключа одним native statement: `ON CONFLICT` на PostgreSQL и SQLite, `ON DUPLICATE KEY UPDATE` на MySQL и MariaDB. Новая строка получает `key + data + onInsert`; у существующей обновляются только колонки `data`, а ключ и остальные колонки остаются прежними. В `onInsert` — то, что нужно только новой строке: явный ID, время создания. С пустым `data` существующая строка не меняется. Ключ непустой, без NULL и называет колонки одного уникального индекса или первичного ключа: PostgreSQL и SQLite используют его как цель конфликта и отклоняют ключ без такого индекса, а MySQL и MariaDB обновляют строку при конфликте по любому уникальному индексу таблицы и вставляют ещё одну строку, если ключ не покрыт ни одним из них. Каждая колонка встречается в трёх массивах один раз; `data` не меняет первичный ключ, а колонку мягкого удаления не содержит ни один из них. Новая строка проверяется как в `insert`, поэтому при `generatedId: false` ID передаётся в `key` или `onInsert`. Строка ключа обновляется и тогда, когда она мягко удалена, и остаётся удалённой — восстанавливает её явный `restore`. Affected rows у upsert на разных платформах считаются по-разному, поэтому метод ничего не возвращает: строку перечитывают по ключу.

`lockForUpdate(ids)` блокирует физические строки с этими PK до конца текущей транзакции через `SELECT ... FOR UPDATE`; вне транзакции вызов отклоняется. ID нормализуются и дедуплицируются, строки блокируются в порядке ключа (так конкурирующие транзакции не взаимоблокируются). Большие наборы делятся на statement по 5 000 ключей; целочисленные ключи сортируются до разбиения, поэтому порядок сохраняется и между statement, а строковые ключи следуют collation базы внутри каждого statement. В SQLite строковых блокировок нет, выполняется обычный SELECT. Межпроцессные advisory locks («одна критическая секция на заказ») остаются в приложении.

Несколько операций объединяются стандартным `$db->transactional(...)` на общем Connection. Одиночный CRUD, upsert и `insertMany` в один statement не создают дополнительную транзакцию. Разбитый на несколько statement `insertMany` и операции `LinkSet` используют транзакцию/вложенный savepoint DBAL и пробрасывают ошибки. Автоматические retries отсутствуют.

`LinkSet` предоставляет `attach(id, ids): void`, `detach(id, ids): void`, `sync(id, ids): void`. Входные IDs нормализуются по типу target PK и дедуплицируются; порядок IDs не сохраняется. Attach уже существующей связи и detach отсутствующей — no-op; `sync` устанавливает точное множество, `sync(id, [])` очищает его. Attach/detach пустого списка ничего не делают.

Синхронизация читает все физические pivot-строки владельца, включая ссылки на скрытые soft-delete цели. Фильтры отображения не превращаются в фильтры записи. Для строковых ID LinkSet дополнительно читает канонические ключи через SQL, чтобы attach/detach/sync учитывали collation БД и разные написания одного ID. Ошибки FK/unique не скрываются. Транзакция гарантирует rollback частичного изменения, но не сериализует конкурентные sync/attach автоматически. Если несколько процессов меняют один набор, приложение согласует блокировку владельца или иную стратегию конкурентной записи в общей транзакции.

## Большие выборки и сложный SQL

`iterateById` выполняет keyset batching: `id > lastId`, `ORDER BY id ASC`, `LIMIT batchSize`. Он требует одного неизменяемого ключа DBAL integer/bigint, не принимает другую сортировку и не использует OFFSET/предварительный COUNT. Размер пакета должен быть положительным.

Фильтры, locale, visibility и includes одинаковы для каждого пакета. Память занята текущими владельцами **и их связанными строками**; неограниченный fan-out может быть большим. Завершённые DBAL results освобождаются, история объектов не хранится. Удержание моделей самим потребителем не ограничивается библиотекой.

Это не серверный cursor и не snapshot при конкурентных изменениях. Для согласованного экспорта приложение выбирает транзакцию/изоляцию своей БД. Для произвольного порядка, составного cursor, сырых потоковых строк и отчётов используется DBAL.

У `ReadQuery` нет `toDbal()` в первом релизе: изменение экспортированного builder создало бы второй контракт для alias, проекций и применения политик. Сложный запрос строится на уже инжектированном Connection и может использовать ту же функцию mapper. Soft delete, переводы, type conversion и связи в таком запросе задаются явно.

## Платформы и ошибки

Проверяемая матрица — PostgreSQL 17 (`pdo_pgsql`), MySQL 8.4 и MariaDB 12.3 (`pdo_mysql`) и SQLite (`pdo_sqlite`). CI проверяет минимальную ветку DBAL 4.3 и актуальную совместимую версию. MariaDB обрабатывается как MySQL; SQL Server и прочие платформы не объявляются совместимыми автоматически по наличию DBAL-драйвера; совместимость с более старыми серверными версиями здесь не заявляется.

SQL builder, экранирование, параметры, типы и транзакции делегируются DBAL. Узкие операции, для которых нет нужного общего API, проверяют платформу явно: generated ID и PATCH upsert переводов. Нет ветки «всё неизвестное считаем PostgreSQL» и общего INSERT IGNORE, скрывающего сторонние нарушения ограничений.

Ошибки определения Mapping и неподдерживаемые параметры запроса должны выявляться до SQL насколько это возможно; ленивые связи проверяются при первом разрешении. DBAL-ошибки исполнения сохраняются с причиной. Некорректные результаты mapper/assign — ошибки контракта, а не пропущенные модели.

## Переход с v3

Полная последовательность перехода, изменения схемы и примеры «до/после» находятся в [руководстве по миграции](migration.md). В Solo Repository нет `BaseRepository`, `RepositoryInterface`, старых relation DTO и сервисов v3. Документация v3 остаётся в [репозитории прежнего пакета](https://github.com/SoloPHP/Base-Repository/tree/v3.1.0/docs).

| V3 | Solo Repository |
|---|---|
| Наследование и protected-настройки | `new Repository($db, new Mapping(...))` или типизированный наследник, который задаёт маппинг в своём конструкторе; публичные методы `Repository` final |
| Статический метод mapper по имени | Типизированный callable; `Model::fromArray(...)` адаптируется к преобразованным DBAL значениям |
| Изменяемые/одноразовые `withLocale`, `with` | Независимый повторно используемый `ReadQuery` |
| `find/findBy` на репозитории | `read()->find/findBy`, либо сразу `withLocale/with` |
| `create/update` возвращают модель | `insertGetId/update`, затем явное чтение при необходимости |
| Нет locale — нет translation JOIN | Настроенный `defaultLocale` для обычного чтения; без него нет JOIN, переводимые поля NULL |
| Пустая строка вызывает fallback | Пустая строка — перевод; только NULL/нет строки вызывают fallback |
| Fallback в выводе отличается от фильтра | Одинаковый resolver для вывода, фильтра и сортировки |
| `relation.field` и scope-ключи в массиве | `Filter::related` и обычные функции, возвращающие критерии |
| Связь через публичное свойство repo и имя setter | Lazy callable репозитория и `assign(entity, related): entity` |
| Неявное поведение `deleted_at` в критериях | `Visibility`; отдельные правила видимости связей |
| Произвольные наборы полей в `insertMany` | Один набор полей на вызов |
| `sum/avg/min/max`, `lockForUpdate` | `ReadQuery::sum/avg/min/max`, `Repository::lockForUpdate` |
| Transaction и advisory lock wrappers | DBAL и код приложения |

Автоматический compatibility layer в ядро не включается. До миграции данных нужно решить, какие старые `""` должны стать NULL для сохранения fallback. Обязательны аудит уникальности переводов/pivot/has-one, совпадения типов ключей и ожиданий mapper. Например, mapper, который сам создаёт дату из строки, теперь получает `DateTimeImmutable`; набор доступных колонок определяется Mapping.

## Проверяемое поведение

Интеграционные сценарии проверяют каталог с category/tags, переводы, page limit, атомарную запись и обход по ID. Проверяются независимость locale/includes, same-row/OR/NOT EXISTS, soft delete, проекции, NULL/пустые переводы, typed keys, разбиение пакетов, rollback и `assign`, возвращающий immutable-модель.

Для каталога с category + tags в пределах одного пакета проверяется 4 SELECT: владельцы, category, pivot, tags. Для UPDATE по ID — один UPDATE без SELECT. При переходе keyset на следующую страницу тесты проверяют освобождение объектов завершённого пакета. Производительность в миллисекундах зависит от данных, платформы и схемы и не является обещанием преимущества перед ORM.
